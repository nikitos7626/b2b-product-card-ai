# B2B Product Card AI Assistant · AI-помощник подготовки карточек товаров КИПиА

Прототип промышленного сервиса для автоматической генерации и валидации черновиков карточек товаров контрольно-измерительных приборов и автоматики (КИПиА) для B2B интернет-магазина.

Сервис принимает технические данные о приборе (наименование, производитель, словарь характеристик, фрагмент паспорта) в формате JSON или через веб-форму и формирует готовый черновик карточки с гарантией отсутствия выдуманных характеристик.

---

## 🚀 Быстрый запуск

### Вариант А: Запуск через Docker (Рекомендуемый)
```bash
docker compose up --build
```
Сервис поднимется и будет доступен на `http://localhost:8000`.

### Вариант Б: Локальный запуск на Python

#### 1. Установка зависимостей
```bash
git clone https://github.com/nikitos7626/b2b-product-card-ai.git
cd b2b-product-card-ai
pip install -r requirements.txt
```

#### 2. Настройка переменных окружения
Скопируйте шаблон конфигурации:
```bash
cp .env.example .env
```
В файле `.env` настройте провайдера LLM (Google Gemini или OpenAI):
```ini
# Google Gemini (по умолчанию)
LLM_PROVIDER=gemini
GEMINI_API_KEY=ваш_ключ_google_ai_studio
GEMINI_MODEL=gemini-flash-lite-latest

# Либо любой OpenAI-совместимый API
# LLM_PROVIDER=openai
# OPENAI_API_KEY=sk-...
# OPENAI_BASE_URL=https://api.openai.com/v1
# OPENAI_MODEL=gpt-4o-mini
```
> 💡 *Примечание:* Если ключ не указан, сервис автоматически активирует встроенный детерминированный оффлайн-модуль, позволяя протестировать всю функциональность веб-интерфейса и API без внешних сетевых вызовов.

#### 3. Запуск веб-сервиса
```bash
python -m app.main
```
- **Интерактивный веб-интерфейс:** `http://localhost:8000`
- **Интерактивная документация Swagger OpenAPI:** `http://localhost:8000/docs`
- **Проверка здоровья (Health-check):** `http://localhost:8000/api/health`

## 📋 Что формирует сервис (Требуемый результат)

Для каждого товара сервис генерирует:
1. **SEO-заголовок (тег Title):** строго **до 70 символов** с ключевыми параметрами прибора.
2. **SEO-описание:** связный технический текст объемом **800–1 200 символов** в строгом B2B-стиле (без рекламной «воды» и клише).
3. **Структурированный список характеристик:** таблица параметров. Все значения берутся **строго из входных данных** (при отсутствии параметра — пометка *«данных нет»*).
4. **3–5 поисковых запросов:** семантическое ядро страницы (брендовые, параметрические, коммерческие и паспортные запросы).
5. **Commercial-блок для менеджера по продажам:** целевая аудитория (ЖКХ, энергетика, нефтегаз, пищепром) и решаемые прибором инженерные задачи.
6. **Отчет о полноте данных (Data Quality Report):** выявление отсутствующих критических характеристик и полей, требующих уточнения (например, чисел без единиц измерения).
7. **Форматы вывода:** мгновенное копирование в буфер обмена в форматах **Markdown** и **JSON**.

## 🛡️ Принятые решения и защита от галлюцинаций (Zero Hallucination)

В контрольно-измерительных приборах неверная цифра диапазона или резьбы штуцера ведёт к авариям или срывам закупок. В проекте реализован **двухуровневый барьер проверки**:

1. **Prompt Engineering & Few-Shot Constraints (`app/prompt.py`):**
   - Модель получает жесткую инструкцию: технические характеристики брать **только** из входного JSON.
   - Если характеристика отсутствует во входных данных (например, температура среды, исполнение по взрывозащите), модель обязана ставить значение `«данных нет»`.
2. **Детерминированный Python Grounding Verifier (`app/validator.py`):**
   - Независимый программный код разбирает выходную таблицу характеристик и проверяет числовые параметры по исходному тексту запроса.
   - Если модель добавила выдуманное число, параметр маркируется предупреждением `[⚠️ требует проверки источника]`.
3. **Таксономический валидатор полноты данных:**
   - Сервис использует базу из **238 категорий приборов КИПиА**, спарсенных с реального промышленного каталога `souz-pribor.ru`.
   - Для каждой категории зафиксирован эталонный список обязательных атрибутов (`required_specs`).
   - Если прибор относится к категории «Манометры показывающие», а в запросе не передана присоединительная резьба или класс точности, система явно уведомляет контент-менеджера в блоке замечаний.
4. **Детектор сомнительных значений:**
   - Автоматически находит параметры без единиц измерения (например, `"давление": "16"` — неясно: Па, кПа, бар или МПа) и расплывчатые термины (`"обычная"`).

## ⚠️ Ограничения решения и вектор дальнейших улучшений

### Текущие ограничения MVP:
1. **Отсутствие постоянного хранилища (БД):** по условиям ТЗ сервис работает на лету и не сохраняет историю запросов в СУБД.
2. **Синхронный конвейер:** генерация выполняется в рамках одного HTTP-запроса (при больших очередях селлеров эффективнее асинхронный Task Queue через Celery/Redis).
3. **Локальный веб-интерфейс:** выполнен в виде легковесного SPA без авторизации пользователей и ролевой модели.

### Возможности для масштабирования в Production (Roadmap):
1. **Гибридный пайплайн со спановым экстрактором GLiNER:**
   - Для высоконагруженного продакшена (миллионы товаров) экономически эффективно использовать двухуровневую обработку:
   - Локальный экстрактор **GLiNER** (20–40 мс на прибор) извлекает сущности со 100% гарантией отсутствия галлюцинаций и сжатием факт-листа;
   - **LLM** привлекается только для генерации продающего SEO-текста и коммерческих выводов. Это снижает расходы на токены на 60–70%.
2. **Пакетная загрузка прайс-листов:** обработка файлов Excel/CSV на 10 000+ позиций в фоновом режиме.
3. **Экспорт в CMS:** прямая интеграция через API с 1C-Битрикс, OpenCart или ERP-системой предприятия.
4. **OCR паспортов приборов:** распознавание сканов заводских паспортов и свидетельств об утверждении типа средств измерений (PDF/TIFF) с автоматическим парсингом таблиц погрешностей.
5. **Генерация микроразметки Schema.org Product:** автоматическое добавление JSON-LD скрипта для формирования расширенных сниппетов в поисковой выдаче.
